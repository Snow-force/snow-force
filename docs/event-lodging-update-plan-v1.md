# SnowForce 活动住宿功能详细更新计划

## 2026-11-05 业务规则修订（优先于下文旧版方案）

用户确认：多天活动在活动详情及报名流程中提供可选房型，每种房型配置**每人固定活动套餐总价，已含住宿**。不按整间房另行加收，不要求凑齐同住人数；同住人数变化不改变每人套餐价。工作人员人工安排同住，不提供自动拼房功能。

后台从活动编辑进入房型套餐配置，通用酒店和房型可复用。酒店每晚成本、必付费用及税费估算仅作内部核算，不能作为对客售价，也不能自动分摊形成套餐价。旧草稿未配置套餐价时保持“未设置”，不得推算。

前台正式销售前，须完成每人房型名额预留、服务端套餐校验、不可变价格快照、原有逐人免责与付款、优惠码、取消及退款验证。旧版下文中“第一期整套收费、住宿独立结账”的内容已被本修订替代；酒店整套库存继续作为内部供应基础。

版本：v1.0  
日期：2026-11-03，America/Los_Angeles  
状态：待实施的产品与开发计划  
建议项目文档位置：`docs/event-lodging-update-plan-v1.md`

在现有 Event 报名中加入住宿选择，由后台维护酒店、房型、协议价格和日期库存。第一阶段完成活动关联、整套房预订、住宿独立付款、取消审批与退款；后续支持长期协议房的独立订房入口，再扩展一次合并结账及按床位销售。

核心设计是：**酒店与房型长期复用，库存按实际入住日期共享，活动只是销售入口。** 同一批协议房同时展示在两个活动中，不能因此产生两份库存。

## 1. 需求依据与边界

### 1.1 截图明确表达的需求

| 内容 | 规划要求 | 需保留的事实边界 |
|---|---|---|
| 不同活动的住宿安排可能不同 | 活动单独配置是否提供住宿、可售日期和房型 | 不默认所有活动都必须订房 |
| 房型由 SnowForce 后台填写 | 提供酒店与房型资料管理，支持复制使用 | 首发不依赖酒店实时 API |
| 希望长期经营 Mammoth Mountain Inn 订房 | 酒店、协议和库存独立于单个 Event | 酒店名称按截图作为首个配置候选 |
| 未来雪季可能包下全部 2b loft | 支持协议房、季节库存、停卖和手工占房 | “大约五套”是待酒店确认的数量，不能直接作为线上库存 |
| 协议价较之前自行预订约优惠 30% | 支持成本价、售价和有依据的参考价 | 该幅度来自聊天描述，不能直接作为全年折扣承诺 |
| 两三个月价格基本相同 | 支持价格日历批量填充和例外日期 | 不代表节假日、税费及全部日期价格相同 |
| 住宿可以不赚钱，目标是引流 | 记录住宿来源、带来的注册和活动转化 | 需要核算手续费、空置及取消损失，区分让利和亏损 |

### 1.2 与现有项目衔接

已核对 GitHub 默认分支中的 `AGENTS.md`、`PRODUCT.md`、活动代报名 V2 计划和活动支付相关代码。核对的是项目文件，不代表重新验证了全部生产参数。

- Event 已有本人和朋友代报名模型；每位参加者保留独立报名、名额和 waiver。
- 既有计划确认：同一会员可替不同朋友报名，沿用每场活动现有代报上限；未成年人与监护人规则继续适用。
- 现有活动收款通过 Stripe Checkout，支付尝试与 Pending Registration 关联；代码中设置约 31 分钟的 Checkout 到期时间，并通过既有支付尝试恢复流程处理重试。
- 当前退款服务以 Registration 为核心，包含已绑定支付的唯一性校验。住宿不能伪装成一位参加者，也不能把同一笔住宿付款重复绑定给多个参加者。
- 既有取消规则为申请、管理员审批、独立退款；审批前保留名额。住宿按同样的操作语义扩展。
- 现有项目约定仍写明拼房不属于内置功能。开发本需求时应同步更新产品范围说明，明确新增整套房预订与后续拼房的界限。

## 2. 分期范围

| 阶段 | 交付内容 | 暂缓内容 | 完成条件 |
|---|---|---|---|
| 第一期 活动住宿 MVP | 后台酒店/房型、日期库存、报价、活动关联、整套房预订、独立住宿付款、订单、取消审批、退款和酒店名单 | 按床位拼房、自动配室友、多人合并付款、酒店 API | 从活动报名到住宿确认的完整链路通过验收 |
| 第二期 长期协议房 | 独立住宿页面、日期搜索、季节协议、批量库存/价格、候补、引流统计 | 外部多渠道自动同步、动态收益管理 | 活动入口与独立入口使用同一库存 |
| 第三期 合并结账与拼房 | 活动与住宿统一订单、金额分配、逐项退款；按需增加床位销售 | 未经酒店允许的拆售和自动转售 | 子账本、混合取消及入住容量规则全部成立 |

第一期默认：住宿可选、整套房收费、固定活动住宿日期、住宿全款、USD、已确认协议库存。成人/儿童人数均计入酒店允许的入住人数，床型名称不直接推导人数上限。

需要住宿才能成立的强绑定活动应在支持活动席位与房间联合预留后开放。第一期可选住宿付款失败时，已完成的活动报名保持原状态，并明确告知住宿未成功。

## 3. 第一版用户流程

### 3.1 新用户从活动进入

1. 活动详情页展示“住宿可选”，显示酒店、可订日期、房型、总价计算方式和取消摘要。
2. 用户查看房型资料和余量，预估住宿费用。浏览和选择草稿不占房，也不保证价格。
3. 用户按现有规则完成本人或朋友报名；每人的付款、审批和 waiver 进度独立显示。
4. 报名结果页显示“为本次行程预订住宿”。按尚未完成的参加者状态提示，不把“代报已提交”当作朋友已获准参加。
5. 选择房型、套数和入住人，展示入住/退房日期、晚数、每套价格、全部必付费用、线上应付及到店应付。
6. 用户确认住宿条款后，服务端重新核价并原子预留整段日期的房间；生成住宿订单和对应 Stripe Checkout。
7. 支付后由服务器核验，订单进入已确认或明确的异常核对状态；浏览器返回成功页不是确认依据。
8. “我的行程”同时显示活动报名卡和住宿订单卡，两者各自标明付款、取消、退款状态。

第一期会出现活动费和住宿费两笔付款。活动详情、住宿入口和付款前都应说明，避免用户把活动押金误认为包含房费；不能把这套流程宣传为一次统一付款。

### 3.2 已报名用户补订住宿

在“我的行程”点击“添加住宿”，直接进入该活动允许的房型和日期，复用现有参加者资料。付款前重新检查库存、入住人数、报名归属和房价。

### 3.3 只替朋友报名的用户

Booker 可以付款和管理住宿，不必本人入住或参加活动。入住人名单与 Booker 分开；选定的朋友必须是其有权管理的参加者。未签 waiver 的参加者不因此获得活动资格，住宿入住确认也不替代活动签到。

### 3.4 手机页面要求

- 房型卡展示真实照片、床位结构、最多入住人数、设施和“每套/每晚”或“每套/全程”的计价单位。
- 固定日期的活动直接显示日期和晚数，首发不用通用酒店搜索表单增加操作量。
- 确认页显示总额和退款摘要，再进入付款；必付费用不能只在最后一步才出现。
- 售罄时给出候补入口或其他可售房型，不保留可付款按钮。
- 请求发出后立即给出反馈，禁用重复提交；返回页面可继续核对原订单。
- 中英文完整覆盖键盘操作、焦点、错误提示、日期、币种和支付状态。

## 4. 后台功能

### 4.1 酒店资料

字段包括中英文名称、地址、当地时区、照片、简介、设施、入住/退房时间、联系渠道和运营状态。管理员维护资料；公开页面只显示批准公开的信息。

酒店协议另存：合同编号、有效季节、房型与数量、SnowForce 可销售范围、酒店确认方式、成本结算方式、退订期限、未售库存退还期限和税费责任。合同与内部成本对普通会员不可见。

### 4.2 房型资料

支持中英文房型名称、卧室/床/沙发床说明、照片、成人/儿童人数规则、最大入住数、便利设施和附加限制。`2b loft` 先保留为待酒店确认的名称，不能自行解释成“两张床”或确定容量。

房型资料可复制；停用只阻止新销售，历史订单仍读取下单时的名称和政策快照。

### 4.3 库存与价格日历

支持按日期范围批量录入、区分工作日/周末、指定节假日例外、停卖、维修、运营占用、线下售出和库存返还。每次变更记录操作者、原因、前后值和时间。

库存日历至少显示：合同可用、已付款占用、付款中预留、状态待核对、手工锁定、剩余可售。库存不能减少到低于既有有效占用，冲突必须先进入人工处理。

价格日历分开保存内部协议成本和对客售价；批量修改只影响新报价，不覆盖已付款订单。价格变动后已有未付款报价应失效或按明确的锁价规则继续，不能偷偷改变 Stripe 应付金额。

### 4.4 活动住宿配置

每个 Event 配置：住宿开关、关联酒店/房型、入住和退房日期、销售窗口、每个订单最多套数、是否仅限有效活动参加者、可售额度、价格方案和取消政策版本。

第一期只开放“可选住宿”。“必须包含住宿”先作为后续产品能力，不能仅增加一个前端必选框就开放。

### 4.5 订单与运营

后台支持按活动、酒店、日期、会员、订单号、支付/退款状态筛选；查看入住名单、酒店确认号、待办和审计。支持手工占房、确认酒店名单、取消审批、按房间/晚数计算退款和导出酒店名单。

任何手工占房均走同一库存服务，不允许后台绕过容量限制。酒店名单只包含酒店履约所需资料，不包含参加者的活动 waiver 签名、完整生日或其他同行人的付款信息。

## 5. 数据结构建议

以下是拟新增的业务实体，名称待结合完整数据库迁移清单确定；不得把建议表名当成已经存在的表。

| 实体 | 主要内容 | 关键约束 |
|---|---|---|
| `lodging_properties` | 酒店资料、时区、上下线状态 | 酒店可跨活动使用 |
| `lodging_room_types` | 房型、床型、人数规则 | 房型属于酒店，资料变化不改历史快照 |
| `lodging_contracts` | 协议期限、数量、结算和销售约束 | 合同确认前不生成可售库存 |
| `lodging_units` | 协议中的可分配房间或合同库存单元 | 内部编号不冒充酒店真实房号 |
| `lodging_unit_nights` | 每个单元每个入住夜的供给与停卖状态 | 单元与日期唯一 |
| `lodging_rate_nights` | 每晚成本、售价、价格版本 | 金额使用币种最小单位 |
| `event_lodging_offers` | Event 与房型、日期、价格方案的关联 | 指向共享库存，不能复制出新库存 |
| `lodging_reservations` | Booker、日期、套数、状态、政策和报价快照 | 属于住宿订单，不占活动席位 |
| `lodging_reservation_items` | 每套房、夜晚、费用、折扣与税费明细 | 支持后续按一套或一晚退款 |
| `lodging_allocations` | 订单对单元和入住夜的实际占用 | 同一房间夜最多一个有效占用 |
| `lodging_guests` | 实际入住人、关联 Registration、必要身份资料 | 付款人、入住人和参加者分别建模 |
| `lodging_payment_attempts` | Checkout、PaymentIntent、金额与核对状态 | 不与活动 Registration 复用付款绑定 |
| `lodging_refunds` | 退款操作、明细分配、Stripe 状态 | 幂等、并发退款上限和累计金额约束 |
| `lodging_cancellation_requests` | 申请范围、政策、审批和库存释放结果 | 申请本身不释放房间 |

复用已存在的邮件 outbox、后台鉴权、审计和 webhook 去重能力前，应先核实实际表结构；不要为了名称一致再建一套相同设施。

### 5.1 不可变快照

订单保存房型与床型说明、入住日期、每晚售价、费用和税费、折扣、线上及到店应付、取消政策正文/版本、同意时间、入住人数和订单语言。酒店后台后续改名或改价，不能修改顾客已接受的交易内容。

## 6. 库存和防超卖

### 6.1 计算口径

可售房间夜 = 已确认合同供给 − 有效已订占用 − 未结束付款预留 − 支付结果待核对占用 − 运营/维修/线下占用。

入住采用酒店当地日期，区间为 `[check_in, check_out)`，退房日不算入住夜。交易时间统一保留 UTC，界面和销售截止使用酒店时区解释；覆盖夏令时测试。

活动 A、活动 B 和未来独立住宿页面只能读取并扣减同一个库存池。各入口的销售配额只是额外上限，不能增加总供给。后台手工售出也使用同一池。

### 6.2 连续住宿必须可兑现

连续两晚订一套房，必须有同一可用单元覆盖两晚。不能只看每晚剩余数的最小值：第一晚只剩房间 A、第二晚只剩房间 B 时，默认不可承诺无须换房的连续住宿。

酒店尚未提供具体房号时，可按合同建立内部单元，前提是酒店保证该类别的连续住宿分配；否则需要酒店先确认库存再售卖，不制造虚假房号或保证。

### 6.3 原子预留

1. 服务端确认身份、活动规则、入住人数、日期、报价和房间数量。
2. 在一个短数据库事务内，按稳定顺序锁定候选单元及全部所需日期。
3. 检查整段日期的供给和占用，创建订单、全部房间夜的占用和支付尝试草稿。
4. 任一夜不足，则整笔住宿预留失败，不留下半段住宿。
5. 提交数据库事务后再请求 Stripe，避免外部网络调用长时间持有数据库锁。
6. 以数据库唯一性/冲突约束作为最后保护；前端余量、进程内锁或缓存不能独自承担防超卖。

同一 Booker 的重复点击复用请求幂等键。不同浏览器标签页、后台手工登记和两个活动入口必须参加同样的竞争。

### 6.4 付款预留过期

沿用活动现有约 31 分钟 Checkout 尝试的思路，为住宿独立保存 Stripe 实际 Session 到期时间。创建会话前的短期预留可以有独立超时，但会话创建结果未知时不得仅凭本地计时释放。

清理任务先核对权威支付状态：确认未付且 Session 已失效后释放；支付处理中或结果不确定时继续锁定并进入核对。清理、用户恢复付款和 webhook 必须用同一原子状态转换协调，不能相互覆盖。

## 7. 定价和费用

### 7.1 展示口径

住宿应付 = 各套房各入住夜售价合计 − 适用住宿折扣 + 必付服务/清洁/额外人数费用 + 按相应税基计算的税费及评估费。

每条费用明确：按订单/按套/按晚/按人计算，是否可退，是否在线收取，是否已经包含在酒店协议价中。可退损坏押金与住宿收入分开显示，若由酒店到店收取，也要在付款前说明。

第一期默认住宿全款。酒店到店押金或酒店与 SnowForce 之间的合同定金，不应混入现有活动的 `$99` 押金字段。分期、尾款提醒和续住在后续独立扩展。

活动优惠券默认不作用于住宿；需要住宿优惠时明确适用房型/日期、额度、叠加规则和成本承担方。促销预算不能被当作库存或酒店确认依据。

### 7.2 协议优惠与宣传

“约便宜 30%”只用于内部商业假设。对外展示比较价须有相同日期、房型、入住人数、取消条件和必付费用口径的可追溯参考报价；否则只展示 SnowForce 对客价。

可先批量填充两三个月相同房价，再显式覆盖酒店确认的旺日和限制。价格规则带生效时间，避免将未来雪季复制为当前雪季。

### 7.3 税费配置

住宿使用独立税费规则，不能直接复制商城商品 sales tax，也不能因活动可能有不同处理而把住宿设为免税。Mammoth Lakes 官方资料分别列有 TOT 和 TBID，并说明住宿的一些必付附加费可能计入相关税基；实际收费和申报安排须结合酒店合同确认。

上线数据必须明确：酒店是否已含税报价、谁向客人收费、谁负责申报、哪些费用计税，以及适用日期。系统保存税费名称、规则版本、税基、金额和收取方，防止重复收费；不在代码中写死一个永久税率。

官方参考：[TOT 信息](https://townofmammothlakes.ca.gov/201/Transient-Occupancy-Tax-Information)、[TBID 信息](https://www.townofmammothlakes.ca.gov/551/TBID)。本计划不判定 SnowForce 在具体合同中的税务身份。

## 8. 支付与订单一致性

### 8.1 第一期独立住宿收款

沿用站点既有 Stripe Checkout 方式，建立住宿专用 checkout/fulfillment/reconciliation 逻辑。现有活动报名与退款记录继续对应原 Registration，住宿对应 Reservation。

共享 webhook 入口按数据库可验证的业务归属分派至活动或住宿处理器。Metadata 可携带关联 ID，但不能作为金额、权限或收款成功的依据；服务端必须核对订单、币种、金额和当前支付尝试。

### 8.2 确认与异常

- 签名验证、Stripe 事件去重和业务订单幂等同时保留。
- 通过服务端读取真实支付状态，核实金额和币种后，再原子完成支付入账、房间占用确认和待发送通知记录。
- 支付成功但浏览器未返回，webhook 仍能履约；返回页只查询或触发同一个幂等核验过程。
- Session 创建响应丢失，用原幂等尝试恢复；旧尝试未核清前不创建另一笔收款。
- 数据库短暂故障不丢弃事件：允许重投并提供定期对账修复；通知失败独立重试，不撤销已支付订单。
- 已付款但出现供给异常，保持款项记录并进入人工处理，不静默丢单，不再出售该房间夜。
- 如果支付方式有延迟确认，订单显示处理中并继续占用，最终成功/失败走对应事件。首发只开放能够完成库存占用及失败恢复验证的支付方式，配置范围限定住宿业务。

Stripe 官方明确要求履约能够处理重复及并发调用，且不能只依靠成功跳转页：[Checkout 履约指南](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page)。

### 8.3 后续合并结账

统一订单应有活动费、住宿费、税费、折扣和退款的分项账本。若合并承诺活动与房间同时成功，必须联合预留全部资源；不能先收活动费再承诺一定有房。

一个 PaymentIntent 通过订单账本分配到多个业务项目，不能直接塞进每个人的唯一支付字段。支持只取消一个朋友、只退一套房、整单取消，以及金额舍入后的逐分对账后，才开放合并支付。

## 9. 状态设计

| 维度 | 建议状态 | 必须保持的区分 |
|---|---|---|
| 住宿订单 | draft / held / awaiting_payment / confirmed / cancelled / completed / needs_review | 付款处理中不等于已确认 |
| 付款 | not_started / creating / open / processing / paid / failed / unknown | 网络超时不等于失败 |
| 取消申请 | none / requested / approved / rejected | requested 仍占房 |
| 退款 | none / creating / pending / partial / succeeded / failed / unknown | 批准取消不等于退款到账 |
| 酒店履约 | not_required / pending / acknowledged / issue | 若需要酒店逐单确认，应先确认再收款或明确采用另一套预约产品 |
| 运营入住 | not_arrived / checked_in / checked_out / no_show | 活动签到与酒店入住分别管理 |

库存占用由明确的分配记录和原子业务状态控制，不能通过一串模糊的界面标签反推。

## 10. 取消、变更与退款

### 10.1 标准取消

1. Booker 提交取消申请，可指定整单或一套房；展示下单时政策和预计可退金额。
2. 申请期间保留住宿，避免申请被拒时房已售出。
3. 管理员核对截止时间、酒店条件、是否已入住及线下变更。
4. 批准时原子取消相应住宿权益，并根据合同决定恢复可售或转运营锁定；保存库存变更与审计。
5. 独立执行退款，核对 Stripe 结果；并发退款先预占可退款额度。
6. 退款超时或未知时先对账，不能创建新的退款操作碰碰运气。页面分别显示“住宿已取消”和“退款处理中”。

### 10.2 常见特殊情况

| 情况 | 第一期处理 |
|---|---|
| 只取消一个朋友的活动 | 不自动退整套房；提示检查入住名单及住宿是否仍需要 |
| 只取消住宿 | 活动报名保持原状，独立处理住宿政策 |
| Booker 不再参加，但朋友继续入住 | 允许经验证变更联系人；入住名单与活动资格分别核对 |
| 换入住人 | 同一容量内经审核变更并保留历史；新参加者独立完成活动报名/waiver |
| 改日期、房型或增加套数 | 重新报价和预留，明确补退差价；新方案成立前不能先放掉原房 |
| 活动整体取消 | 生成关联住宿待办并按已披露政策处理，不以活动取消直接假定酒店可全退 |
| 酒店无法履约 | 人工替代方案或退款；未经客户接受不能自动换成明显不同产品 |
| no-show、天气或道路关闭 | 按订单政策及实际酒店处理记录执行，不自动套用活动押金规则 |

为控制首发复杂度，自助页面只开放申请取消；日期和房型变更由后台处理，但仍必须经过统一库存与资金服务。

## 11. 与代报名和 waiver 衔接

- 每位实际活动参加者保留一个有效名额，沿用现有代报人数配置；同一套房可关联多人，一位参加者不能因此被重复收费。
- 成年朋友按既有规则本人签署；未满 18 岁由监护人签署，未满 14 岁的现场陪同规则继续生效。
- 一次房费支付只购买住宿权益，不代表替所有室友签署活动免责。
- 住宿条款由付款/预订人确认；酒店如另要求入住人文件，另建所需记录，不能覆盖活动签署证据。
- 参加者已取消、未获批或 waiver 未完成时，后台提示关联风险；不直接联动退房或退款。
- 收集入住人资料以酒店履约需要为限，避免为了订房再复制一套完整儿童生日和监护资料。

## 12. 长期协议房与引流

第二期在酒店/房型/库存服务上增加独立住宿页面，允许不从 Event 进入的会员预订。活动报名是推荐入口，独立住宿订单不虚构活动名额。

管理员按明确季节录入协议，支持连续日期、例外停卖和库存返还截止。截图中的“下个雪季”不直接转换为一组日期，需以酒店签署的季节起止和实际确认数量为准。

后台展示每个协议的可售房间夜、已售房间夜、空置承诺成本、退款损失、净收款和到期动作。已支付给酒店的整季包房成本不能只摊到已售夜而把未售部分隐藏。

增长指标采用明确归因窗口，例如以运营确认的窗口统计住宿新会员后续活动购买；将真实成交和浏览区分。建议指标如下：

| 指标 | 口径 |
|---|---|
| 入住库存售出率 | 已确认已售房间夜 / 已开放可售房间夜，排除明确停卖但另报其规模 |
| 包房履约率 | 酒店确认可交付订单 / 应交付订单 |
| 住宿带来的新会员 | 首次注册且从住宿入口进入的可归因会员 |
| 后续活动转化 | 指定观察期内有已支付活动订单的住宿新会员 / 该批住宿新会员 |
| 每名新增活动客的补贴 | 可归因住宿补贴成本 / 新增已支付活动客数 |
| 住宿净贡献 | 客户净收入扣除代收税费、全部协议成本、支付/退款/运营成本后的金额 |

不固定假设 Stripe 费率。用实际支付方式和账单计算：售价可以接近成本，但管理层必须看见含空置损失后的整季结果。

## 13. 权限、隐私和运营通知

会员只能读取自己有权管理的住宿订单；被邀请入住的朋友只接收本人必要信息。酒店不获得 SnowForce 的其他活动资料，客服按必要范围查看订单，财务与库存管理权限分开评估。

新表明确 grants 和 RLS，公开接口只提供可公开房型、价格和汇总余量。服务端特权访问保留后台鉴权，不能把 service-role key 放进客户端。变更日志不记录支付密钥、完整邀请 token 或多余身份资料。

通知包括付款确认、取消申请与决定、退款状态、入住提醒和名单变更。复用现有投递设施并记录发送/失败状态；邮件失败不影响已支付库存，管理员可查看失败并重发。媒体授权与营销订阅仍为独立选项，不能借住宿付款默认勾选。

## 16. 验收矩阵

### 16.1 产品和资料

1. 无住宿活动完全按现有方式报名，历史订单可查、取消、退款和签到。
2. 后台只录入一份酒店房型，两个 Event 可以关联但不会增加库存。
3. 房型人数、儿童、日期和最少晚数限制在服务端强制执行。
4. 中英文房型、条款、总价、到店费用和取消摘要准确，手机操作完整。
5. 修改房型/价格/条款后，已下单内容仍保持原快照。

### 16.2 库存

6. 一套剩余房间被多个客户端、两个活动和后台同时争抢，只成功一次。
7. 两晚只有不同单元各剩一晚时，不能错误确认连续住宿。
8. 多套多晚的任一晚不足，整笔住宿预留不成立，没有零散占用。
9. 支付预留、已支付、人工锁房和待核对状态均扣减可售。
10. 退房日相接、当地时区、夏令时、售卖截止和库存返还期限正确。
11. 清理与付款成功同时发生，最终只保留一个合法结果，不超卖。
12. 同一订单重试不重复占房；手工下调库存不能穿透既有订单。

### 16.3 资金

13. 正常付款、3DS、中断返回、失败、重复点击、多标签页均可恢复。
14. 支付成功后未回站，仍生成正确订单；重复及乱序 webhook 不重复履约。
15. Stripe 创建请求超时、金额/币种不符、数据库失败和延迟确认均进入可核对状态。
16. 两个管理员并发退款，累计退款不超过实收且明细分配正确。
17. 退款成功但页面超时、退款回调迟到或失败，不会重复退款或错误恢复房间。
18. 线上金额、到店金额、税费和可退押金的合计及舍入可逐项复算。

### 16.4 取消和参加者

19. 提交取消申请仍占房；批准后按政策释放或转锁定；退款状态独立。
20. 取消一个朋友只影响该活动报名，不自动取消同行整套房。
21. Booker 不参加但朋友参加和入住，权限、名单、waiver 均正确。
22. 未成年人规则、监护人签署和现场陪同规则继续生效，住宿不绕过活动资格。
23. 活动整体取消和酒店无法履约均生成明确待办，未处理资金可查。

### 16.5 权限和回归

24. 其他会员不能通过猜 ID 读取或变更订单；酒店导出不含多余隐私资料。
25. 邮件失败可查可重试；不会把仅记录日志当成已发送。
26. 现有商城、活动付款、朋友邀请、取消审批和退款均无回归。
27. 按项目要求运行 `npm test`、`npm run build`、`npm run test:coverage`；库存并发还必须使用隔离 PostgreSQL 验证数据库约束。
28. 使用不指向生产回调的 Stripe Sandbox 和测试收件箱完成联调；本计划不触发真实扣款、退款或通知。

## 17. 性能与可观察性

鉴于已有加购和付款等待问题，新功能应记录查询、报价、数据库锁、预留、Stripe 创建、webhook 和订单确认的分段时间及关联 ID。

建议目标：点击后约 100ms 内出现反馈；常规余量查询 p95 ≤ 1 秒；不含外部支付等待的报价/预留 p95 ≤ 2 秒。它们是待验证的验收目标，不是当前实测；需分别采集移动/桌面、冷/热请求和实际样本。

酒店照片和介绍可缓存；可售余量只能作为展示参考，预留时必须重新读取权威库存。避免逐房型多次往返，支持按日期批量查询。前端把超时显示为“正在核对”，提供原订单查询入口。

监控超卖、付款结果未知、已付未确认、预留超期、待退款、酒店未确认和邮件失败。任何库存或金额一致性异常立即停止新增销售，保留查询和处理已有订单能力。

## 18. 上线与回退

1. 先核实生产当前结构并备份；新增表、约束和权限采用扩展迁移，保持历史数据可读。
2. 先发布默认关闭的住宿代码及数据库能力。每个 Event 独立开关，另设全局停止新增销售开关。
3. 录入已确认酒店资料，在隔离环境完成真实交互和模拟支付验收。
4. 以一个活动、一个房型、有限且已经酒店确认的库存灰度；不要直接把聊天中的五套全部设为可售。
5. 核对订单、Stripe 资金、酒店名单和占用记录，稳定后再扩大日期与库存。
6. 回退时关闭新预订，保留支付核对、webhook、订单查询、取消和退款。不能删除已引用数据，不能部署无法识别住宿订单的旧版收款逻辑。

超卖、重复扣款、退款超额、越权读取或订单与酒店供给不符，均为停止放量条件。

## 19. 运营资料清单

这些资料可以在开发过程中补齐；它们决定何时能开放真实销售，无须为了制定和推进计划现在逐项确认。

| 资料 | 所需内容 | 缺少时的处理 |
|---|---|---|
| 酒店与房型 | 正式房型名、照片使用权、床型、最大入住数、儿童规则 | 可做后台草稿，不对外承诺 |
| 协议库存 | 实际可售套数、日期、连续住宿保证、酒店确认机制 | 不生成可售房间夜 |
| 价格 | 逐日期成本、对客价、必付费用、线上/到店支付 | 不开放付款 |
| 税费 | 含税与否、计算规则、收取和申报方 | 保留配置草稿，先核对合同 |
| 取消政策 | 按当地时间的截止、违约金、部分取消、天气/封路、no-show | 不发布不明确的退款承诺 |
| 合同权益 | 是否允许 SnowForce 对客销售、入住名单/联系人和结算安排 | 完成商业确认后销售 |
| 运营交付 | 酒店名单接收方、发送时间、确认号、紧急联系人 | 建立履约 SOP 后放量 |
| 引流预算 | 允许的补贴、未售库存风险、目标活动转化 | 使用可调整预算，不把不赚钱当成无限亏损 |

## 20. 第一阶段完成定义

运营能在后台建立酒店和房型，为活动配置实际可售的连续日期库存及价格；会员能从活动流程完成整套房预订和独立付款；系统能防止多入口超卖并恢复不确定付款；后台能完成取消审批、退款和酒店入住名单交付；原有活动报名、waiver、商城和退款继续正常运行。

本次交付为更新计划。未修改或部署业务代码、数据库、酒店库存与线上支付配置。
