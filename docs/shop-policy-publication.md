# 商城政策发布与订单条款

## 数据存储

沿用现有 Supabase PostgreSQL 的私有 `commerce` schema，不新增数据库或顾客账号。商城专用角色 `snowforce_commerce` 访问原生 Medusa 表；网站顾客继续使用原来的 Supabase 登录。

草稿、发布历史、工作人员标识和请求回执只存在原生 `commerce.store.metadata.snowforce_shop_policy`。公开 `/shop/policies` 从 Medusa 的 `/store/snowforce/policies` 读取已生效版本；不返回草稿、工作人员或 Store 其他 metadata。没有已发布版本时展示未生效状态；服务失败时展示暂不可用，不展示默认建议条款。

首版采用立即发布，不提供倒填或预约生效日期。每次保存和发布都检查 revision，在 Store 行锁内更新专用键，保留仓库、配送等其他配置。网络失败可使用同一 UUID 重试；同一 UUID 不能改用途或内容。最多保留 100 个发布版本，达到上限后阻止发布，不能静默删除仍可能被订单引用的历史。

## 后台操作

进入商城后台 `/app/snowforce-policies`：

1. 填写真实销售主体和售后邮箱。
2. 审阅期限数字与中英文全文，删除消费者权利章节中的“发布前补充”占位句，并核对实际配送范围、运费、仓库和售后能力。
3. 保存草稿；未保存的编辑不能直接发布。
4. 勾选已完成审阅，再点“发布”。服务端再次校验，成功后立即生效。

保存草稿不改变顾客看到的已发布版本。修改政策文本也不会自动修改原生运费、商品价格、库存或既有订单；这些仍在对应的后台功能管理。政策上线不启用自动拒绝超期售后，法定权利和例外由售后审核处理。

## 结账与订单快照

新的结账报价摘要绑定商品、顾客、地址、价格、税费、配送及政策全文。顾客默认未同意，必须明确勾选当前版本才能进入付款；报价或政策变化会要求重新确认。后端只接受版本号和明确同意，不接受客户端上传的条款、金额或购买时间。

在创建付款会话之前，后端将条款全文、版本、生效时间、同意时间、购物车与顾客标识和原报价摘要写入 `cart.metadata.snowforce_policy_acceptance`。顾客可以编辑原生购物车 metadata，因此记录必须带有后端 HMAC；签名由现有私有 `JWT_SECRET` 经独立用途派生，不是顾客密码，也不增加新的登录界面。签名不会包含或暴露 JWT 密钥。JSONB 重新排序后仍能正确校验。

政策已被接受且付款开始后，恢复该笔付款继续使用已签名版本。验证按准确的不可变历史版本进行，避免并发发布事务的提交先后顺序使已接受付款失效。原生购物车锁覆盖确认记录保存与付款会话创建；每个关键异步边界会检查锁租约，失效后不再启动新的付款操作。

原生 `completeCartWorkflow` 的验证 hook 同时检查工作流最初取出的购物车和当前重读数据；HTTP 完成与 Stripe webhook 自动完成都运行该检查。Medusa 原生订单创建直接复制已校验的 cart metadata，所以条款随订单创建保存，而不是靠事后事件补写。订单保存公开条款和绑定证明，不保存工作人员、草稿或 Store 私有 metadata。此阶段尚未为会员订单页面增加历史条款的独立阅读面板，也未用真实付款验证订单创建。

`JWT_SECRET` 在未完成的购物车仍需要校验时必须稳定。轮换前先处理现有付款会话，否则旧签名会失效，需要后台恢复；已经保存的订单条款全文不会因此消失。

## 当前验证与上线条件

真实 `snowforce_commerce` 角色已运行保存、发布、幂等、专用键保留和 JSONB 签名的源码事务测试，全部强制回滚。Store metadata 和 updated_at 完整恢复，政策仍未永久保存或发布；订单、退款、资金核对及历史记录仍为 0。测试没有调用 Stripe 金融操作。

主站完整测试、覆盖率和构建已通过。后台完整测试、覆盖率、类型检查和 Admin 构建结果记录在 `docs/shop-verification.md`。

距离正式收款仍需真实主体和邮箱、商城管理员邮箱、实际商品售价/库存/发布、California Seller’s Permit 状态及税务方案确认、生产 TLS Redis 和商城服务部署、正式 webhook、真实测试环境购买/捕获/发货/退换/退款验收。政策发布不会自动开启 `COMMERCE_TAX_POLICY_CONFIRMED`。

还需完善远端已取消 Stripe PaymentIntent 的会话恢复：Medusa 原生 webhook 忽略 canceled，单看本地 pending 可能反复恢复已取消的付款。已定位为上线前待处理事项；不能把新政策链路通过当成整套支付生命周期验收通过。
