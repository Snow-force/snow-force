# Unfinished checkout cancellation

Implementation batch for `SnowForce_商城优化实施计划_v1.md`, executed on 2026-10-15 Los Angeles time.

The authenticated customer preview and confirmation endpoints are `GET/POST /store/snowforce/checkout/:id/cancel`. Both require a registered customer bearer, ownership before provider access, and the existing checkout and native cart leases. Management mode keeps both closed. POST accepts only the preview token and explicit `confirmed: true`; browser cart, payment, account and money fields cannot select a PaymentIntent.

Browser validation found that installed Medusa 2.21.2 replaces thrown conflict messages with generic idempotency guidance. The edit route now returns an explicit 409 `checkout_locked` business response at this one boundary, retaining the previous English message for old storefront compatibility. A real Express test using the installed Medusa error handler covers this transformation; authorization and unknown service failures retain their original handling. The new storefront recognizes the fixed route/status/code rather than relying only on a full English sentence.

The server binds the current native cart, collection and single Stripe session, exact USD cents, mode, original quote and session metadata. It checks native order/payment/authorization history and fresh Stripe funds and expanded charge evidence. Only unfunded, unauthorized `requires_payment_method`, `requires_confirmation` and `requires_action` payments are candidates. Processing, authorized, paid, refunded, foreign or uncertain evidence prevents edits. Provider charge identifiers are opaque strings; failed alternative-method records can use a `py_` prefix.

A versioned operation is stored in the privileged existing payment session metadata before cancellation. It records the actual Stripe account, original identifiers, amount, token and phase. Native monetary/provider data and unrelated metadata are preserved. Cancellation uses a stable session idempotency key. A lost response is reconciled by retrieving that same PaymentIntent; retries never create a replacement intent. An unresolved operation freezes payment preparation and keeps the old client secret out of checkout review.

Stripe state can change outside local leases. Fresh checks immediately before the external request and after its result, expanded charge evidence, and the existing native recovery transaction independently decide whether editing is safe. A cancel/confirm race with authorization evidence stays protected for reconciliation; the application does not treat a canceled string alone as proof of no funds. A pending operation with such evidence may require operator reconciliation rather than ordinary cart editing.

Only provider-confirmed cancellation followed by native recovery and private tax quote/policy withdrawal returns `editable`. Withdrawal reacquires the same leases, so a replacement payment blocks it. Historic retries verify the retained original operation even after native link retirement. Item deletion is a separate action with a new successful native edit fence and an exact line identifier. Closing the customer confirmation performs no cancellation.

Local PostgreSQL and the supplied Stripe Sandbox were used for the real HTTP integration check: 43 requests verified unfunded cancellation, 3DS `requires_action` cancellation, repeated confirmation, native retirement, cleared quote/consent, removal of the final item and refresh persistence. A real manual card authorization remained blocked by preview and edit; its test authorization was subsequently canceled for Sandbox cleanup. No production writes occurred in these tests. Evidence: `output/incidents/plan-v1-native-cancellation.json` (local runtime artifact, not a public deployment asset).

The production-build localhost browser also verified both customer paths with a temporary synthetic member: dismissing confirmation retained the original payment form; cancel-to-edit removed its secret, restored address input, required fresh policy agreement and automatically recalculated tax; a subsequent unfinished checkout could be canceled from the cart and the item deleted. Reload retained the empty cart. Both Sandbox intents ended canceled with zero received/capturable funds, both native sessions and cancellation ledgers remained, and no orders were created. Evidence: `output/incidents/plan-v1-browser-cancellation-verified.json` and the matching local screenshots.
