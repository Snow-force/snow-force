# 退换货操作与数据方案

更新时间：2026-10-01。代码、数据库权限和接口验证已完成；真实会员申请、管理员收货、退款和换货的完整联调仍待经营配置。这不是上线收款验收。

## 数据与登录

仍使用现有 Supabase 项目 `bhmwxkynhyhquspiyact`。商品、库存、价格、订单、支付、履约和原生退换货属于 Medusa 的私有 `commerce` schema；申请与审核记录存于 `commerce.snowforce_after_sales`。没有新增数据库或客户账户。

顾客使用原来的 Supabase 登录页。Next 服务端验证当前会员，再取得关联的 Medusa customer token；后台从不可变 Supabase provider UUID 核对本人订单。浏览器不获得数据库连接、服务端密钥或后台 token。Medusa staff 登录继续供运营人员使用。

申请表保存 UUID、订单/customer/会员 UUID、类型、原因、说明、商品行 ID/数量、状态/版本、顾客回复、内部备注、原生处理关联、退回承运商/追踪号和审核时间。状态历史只包含顾客可见回复。价格、退款金额和库存继续由原生订单工作流维护。

表和触发函数属于 `snowforce_commerce`；游客、普通会员及主站 service_role 无直接读写权限。RLS 开启，由拥有者的后台服务操作，不建立顾客直连 policy。Security Advisor 的 [RLS 无 policy 信息提示](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)符合此私有访问模型；顾客读取由 API 身份及归属校验控制。

## 顾客操作

1. 在“我的订单”打开本人订单详情，选择已送达且仍可申请的商品数量、退货/换货、原因和说明；换货可以说明希望更换的尺码或颜色。
2. 提交后查看审核进度。待审核可以撤销；同一订单同时仅允许一个进行中申请。
3. 批准后按会员订单中的实际指引寄件，再填写承运商与追踪号。
4. 在原有订单查看处理进度、回复和实际物流。

可申请数量为原生 `delivered_quantity - return_requested_quantity - return_received_quantity - written_off_quantity`，下限零。批准时再次核对。后台已按订单购买时接受的政策和实际商品送达记录校验普通退换货期限；超期或证据不完整的普通申请必须明确批准例外并记录原因。质量问题和错发不因普通期限自动拒绝。日期按太平洋时间的日历日和原始申请时间计算，避免审核延迟改变资格；分包交叉期限需要人工核查。实际经营政策仍待运营确认发布，详见 [退换货期限审核](shop-return-window.md)。

## 后台操作

1. 进入 Medusa `/app` 的 **SnowForce returns**，从待审核列表选择申请，检查商品、数量和说明。
2. 填写顾客回复，批准时给出实际退回地址、条件和运输指引；内部备注仅工作人员可见。回复保存到会员订单，本版不自动发邮件。
3. 批准后点“打开订单”，在原生工作区创建对应 Return 或 Exchange，选择准确商品及数量；换货规格、库存和价差由原生后台处理。
4. 返回申请，刷新并关联原生记录；系统拒绝他人订单、类型/数量不匹配、历史旧记录、取消记录及重复关联。
5. 实际收货后在原生后台登记重新入库或报损数量，按情况退款、处理价差与换货发货。申请和批准本身不会执行这些动作。
6. 使用“核对 Stripe 款项”查看当前资金；它只查询和保存核对记录，不发起退款。填写最终回复，点击“核对并完成”。要求全部原生收货、订单 `pending_difference` 为零；换货还要求替换商品已送达。完成操作另行实时核对 Stripe 实收和成功退款金额，pending / requires_action 或金额不一致时保留处理中。

原生失败、取消或特殊售后须人工核查；顾客撤销仅限待审核。正式退款、库存和交运须经过 Sandbox 及真实经营数据验收。
