# 购买政策与退换货期限审核

日期：2026-10-01。此实现是上线准备的一部分，政策仍为草稿，没有发布或创建实际订单。

## 期限的依据

后台审核读取原生订单中购买时保存的政策快照，验证 HMAC、实际 order_cart 关联、顾客、同意与订单创建时间，并核对 Store 中准确的已发布历史版本。不会把当前草稿或较新的政策套到旧订单，也不会从代码默认使用 30 天或 14 天。

以美国太平洋时间的日历日期计算：原生商品送达日加购买政策的 return_window_days，最后一天整天都在期限内。按照申请 created_at 判断是否及时，而不是管理员打开或批准时的日期。跨月、闰年及夏令时切换均有测试。

每个申请商品读取对应的未取消原生履约送达记录。所有相关配送都在期限内时正常审核；所有配送都超期时标明超期；分包期限交叉、缺少日期、日期不一致、政策签名或历史版本无法核实，需要人工核查，不推测哪一批商品被退回。

## 顾客与管理员

会员订单详情的退换货区域现在显示本订单的购买政策版本、完整双语条款及每件商品的普通申请截止日期。分批送达显示日期范围并提示客服核查；无法验证原签名/历史时不套用当前政策或代码默认期限。已批准申请显示原购买政策的交运截止日，填写追踪号不作为实际交运证明。

顾客只接收公开政策内容与日期投影。后端先核对本人原生订单及 Supabase 会员绑定，再读取一次历史政策；不返回签名、购物车原始 metadata、内部备注或审核人员资料。切换订单时重建售后组件，避免显示上一订单的申请或条款。

顾客仍可在线提交申请，不会因年龄自动拒绝质量问题、运输损坏或错发的处理。所有申请继续检查本人订单、已送达和可退数量，并由后台审核，不自动退款或恢复库存。

普通原因（size / other）超期或证据不完整时，后台批准必须明确勾选政策例外，并在内部备注解释原因。服务端在实际批准时重新核验，不能只依赖页面提示。后台记录例外说明、审核人和审核时间；批准后仍可查看内部审核备注。顾客接口不返回内部备注。

质量问题及错发（quality / incorrect）仍按实际情况审核，普通退换货期限不自动排除消费者权利。管理员可以拒绝申请并说明原因；此实现没有擅自认定具体申请的法律结论。

订单政策签名无法验证（包括旧签名密钥轮换）时，普通申请进入需明确人工例外的审批，保留原始快照，不使用新政策替换。数据库读取失败则停止批准，不把连接失败当作空历史。

## 批准后交运

已批准申请显示按原购买政策的 approved_dispatch_days 和实际审核日期计算的交运截止日期。原生退货或换货的创建时间、顾客填写追踪号的时间，都不能单独证明实际交给承运商的时间。

因此实际交运仍由管理员核对承运商交运凭证，不能以后台处理延迟自动拒绝已经及时寄出的包裹。本轮没有接入承运商扫描事件或交运凭证上传，也没有把填写追踪号伪装成已验证交运。这一交运证据链仍属于上线前待验收工作。

## 数据与验证

没有新表、迁移或权限变更。窗口评估从现有原生订单、履约、order_cart、Store 政策历史实时生成；例外说明写入现有私有申请表的 internal_note，并保留现有版本校验、审核人和时间。未改动商品、价格、库存、运费、税务开关或任何资金记录。

核心窗口及购买政策验证有普通边界、分包、时区、历史版本、归属、篡改、缺失证据、密钥轮换与网络错误测试；实际 React 18 Admin 组件测试验证例外勾选、必填说明、服务端冲突后的重新确认和批准后的备注可读。全部检查结果见 [商城验证记录](shop-verification.md)。

这些为源码和隔离测试验证，不能替代真实商品的购买、送达、退货和承运商流程验收。
