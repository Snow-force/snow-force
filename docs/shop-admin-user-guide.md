## 3. 第一次使用：先准备一个商品

建议先把一款真实现货商品准备完整，保存为草稿，再用同样的方法处理其他商品。

1. 打开 **Products**，选择一个已有草稿，例如 `vector-insnow-dusk`。
2. 核对商品名称、说明和照片与实物一致。
3. 准备实物有售的颜色、尺码及每个组合的 SKU。
4. 在 **Options / Variants** 补齐规格；不要把图册中的所有候选组合直接认定为库存。
5. 每个规格填写正式 USD 售价，打开 **Manage Inventory**，关闭 **Allow backorders**。
6. 在 **Inventory** 为这些 SKU 关联实际 Irvine 仓库并登记现货数量。

8. 商品资料完成后，在 **SnowForce product tax** 审核商品分类。

## 4. 新品、规格和商品发布

### 4.1 编辑已有草稿或创建新品

打开 **Products**，点商品进入详情；新增商品则使用 **Create**。先保存为草稿，分次补资料。

| 资料 | 怎么填写 | 完成后的核对 |
| --- | --- | --- |
| Title | 清楚的英文商品名称 | 英文商品页使用当前 Title |
| Description | 材质、用途、保养、实际确认的功能 | 不把未核实的图册卖点当实物保证 |
| Handle | 稳定、唯一的英文路径标识 | 对应 `/shop/handle`；已分享的商品不随意改路径 |
| Media / Thumbnail | 上传商品照片，选择封面，调整顺序 | 正面、细节、颜色、尺码信息可读；图片不包含人民币价格 |
| Options | 实际颜色 `Color`、尺码 `Size` | 选项值与实物及可售组合一致 |
| Variants | 每个实际可售组合建立规格 | SKU、选项、美元价格、库存关联准确 |
| Sales Channels | 主站公开 key 关联的销售渠道 | 商品、仓库及网站使用同一渠道；不另建同名渠道代替 |
| Shipping Configuration | 已建立的实物商品配送配置 | 所选仓库有适用于该商品的配送方式 |

新增颜色或尺码以后，仍要创建对应 **Variant**；只有选项名称不会产生可售 SKU。不存在的组合不要创建，也不要使用 `To confirm` 作为正式销售规格。商品编辑入口依据：[编辑商品](https://docs.medusajs.com/user-guide/products/edit)。

现有草稿照片已存入商品 Storage。运营人员从 Media 上传新图片还依赖后台 S3 配置，当前未完成上传的浏览器验收；上传失败或前台无法显示时，请技术人员核对商品图片服务及公开 HTTPS 地址，不用本机临时路径替代。

### 4.2 管理每个颜色 × 尺码组合

1. 在商品详情 **Variants** 区域点击 **Create**，选定颜色、尺码并填写规格名称。
2. 填写唯一 SKU；采用你自己的规则，不重复使用另一规格的 SKU。
3. 对美国现货商品打开 **Manage Inventory**，关闭 **Allow backorders**。
4. 在价格步骤填写 USD 正式金额，保存。
5. 进入库存管理，完成仓库关联与实盘数量。

关闭库存管理会使规格被视作不受库存数量限制；打开预订会允许缺货继续卖。两者都不符合本商城默认的美国现货经营方式。首版普通单件商品不要启用未验收的库存套件或组合商品。原生步骤依据：[商品规格](https://docs.medusajs.com/user-guide/products/variants)。

### 4.3 品牌、前台分类和中文资料

在商品 **Metadata** 编辑器中，可维护以下字符串字段；它们保存在后台数据库，无需改前端代码。

| 字段 | 填写内容 | 前台作用 |
| --- | --- | --- |
| `snowforce_brand` | 实际品牌，例如 VECTOR、BURTON | 品牌展示与筛选；没有填写时显示 SnowForce |
| `snowforce_category` | 从下列四个值选一个 | 前台品类筛选；没有填写时归入 accessories |

| 分类值 | 对应品类 |
| --- | --- |
| `outerwear` | 成人雪服 |
| `kids` | 儿童装备 |
| `goggles` | 雪镜 |
| `accessories` | 配件 |

**当前中文编辑存在一个实际限制。** 现有草稿的中文标题、描述及颜色翻译分别来自 `snowforce_name`、`snowforce_description`、`snowforce_candidate_colors` 的双语对象或数组。原生 Metadata 表单会锁定对象和数组，不提供它们的可视编辑；把 JSON 文本贴成字符串不能代替双语对象。

英文 Title / Description 可以正常直接修改；中文需要技术人员通过受认证的后台数据操作维护，仍存数据库，不需要把商品内容写死在代码。新增商品未提供中文对象时，中文页面会回退显示英文。发布前在前台切换 CN / EN 检查。这一限制待补充专用双语商品编辑界面后再更新本手册。

- [ ] 图片和商品资料已核实，中文与英文显示已检查。
- [ ] 真实规格、SKU、正式 USD 价格已填写。

## 5. 美元价格管理

### 5.1 修改日常售价

1. 从 **Products** 打开商品，在规格或价格编辑区域找到目标 SKU。
2. 修改 USD 价格，逐个核对；同款不同规格可以不同价。
3. 原生价格输入框填写美元金额。例如显示售价 US$129.00 时，输入 `129.00`，不要输入美分整数 `12900`。
4. 保存后刷新前台，选中同一颜色、尺码，核对实际价格。

商品价格按未含税美元填写；结账确认地址后另外计算适用税费。不要自行把税费并入商品售价，也不要用人民币换算参考价代替正式售价。已下单商品按订单原价格和优惠处理，改当前售价不应重算历史订单。

### 5.2 活动价与优惠

临时活动价可通过原生 **Price Lists** 配置，优惠规则在 **Promotions**。先保存草稿并核对适用商品、规格、日期、渠道和状态，再进行独立测试。原生能力说明见 [创建价格列表](https://docs.medusajs.com/user-guide/price-lists/create)。

启用前检查折扣后的商品金额、USD 价格、税额及包邮结果；不要仅看商品卡片划线价。本商城不是对全部原生促销组合都已完成验收，首版先使用已验收的定价与优惠规则。

### 5.3 金额填写速查

| 页面 | 运营人员填写的单位 |
| --- | --- |
| 商品 / 规格价格 | 美元，最多两位小数 |
| Price Lists | 当前价格列对应的币种；本商城使用 USD |
| SnowForce shipping | 美元，例如 `9.95`、`100.00` |
| 数据库与内部税账 | 系统处理精确金额，运营人员不直接改表 |

## 6. 库存、补货和盘点

### 6.1 建立库存和仓库关联

在 **Inventory** 按 SKU 搜索，打开对应库存项目，检查其关联的商品规格及位置。若没有 Irvine 库存行，先为项目添加当前发货仓库的库存位置，再登记数量。

同一个 SKU 的不同仓库数量分别维护。商品属于网站销售渠道、仓库也关联该渠道，才能使用该位置库存；把数量填入错误仓库不会自动变成可发的 Irvine 现货。原生库存和预留说明见 [库存管理概览](https://docs.medusajs.com/user-guide/inventory)。

### 6.2 认识三个数量

| 数量 | 含义 |
| --- | --- |
| In stock / 库存 | 当前仓库登记的库存总量 |
| Reserved / 已预留 | 已被订单或预留记录占用的数量 |
| Available / 可用 | 简单单件商品在该位置的库存减已预留数量 |

不要为了让页面显示“有货”而清除订单预留。库存调整不能低于已预留数量；出现差异，先核查占用订单和实际实物。

### 6.3 补货与盘点

1. 按 SKU 查找正确项目及 Irvine 库存行。
2. 核对实物、待发订单占用及当前登记数量。
3. 打开 **Adjust inventory / 库存调整**，确认窗口显示的仓库和 SKU。
4. 当前原生调整窗口的 **In stock** 填写的是调整后的库存总量。培训例：原登记 10 件，另入库 5 件，目标总量应为 15；不要只输入 5。这些数字只是操作示例。
5. 保存，重新核对总量、预留及可用数量，并记录调整原因。

库存流水或其他操作若明确标为增减量，则按该窗口定义填写，不混用总量与增量。退货可售入库优先通过原生退货收货流程处理，避免订单流程已经回补库存后又手动增加一次。

缺货时保留正确的零可用库存和关闭预订的设置。可售退回、破损报损与盘亏分别记录；不要把损坏品填成可用现货。

仓库地址及服务区域在原生 **Settings → Locations & Shipping** 管理。SnowForce shipping 只改运费和门槛，不改州范围。发货地址改变后，要重新审核经营税务配置，并核对政策中的退回地址；修改政策中的文字也不会自动修改实际仓库。

首版由你自行向承运商购买面单并交运；后台履约不会自动购买面单，也不会自动通知承运商上门取件。

## 8. 配送与退换货政策

入口：**SnowForce policies**。页面并列提供中文、英文内容与实际期限字段。

### 8.1 保存草稿

1. 填写正式销售主体名称和客服邮箱 `Shop@snow-force.com`。
2. 审阅配送、申请审核、商品条件、运费承担、退款换货、退回地址、消费者权利七部分的两种语言。
3. 核对期限字段与正文一致。
4. 点击 **保存草稿 / Save draft**。草稿不会自动成为顾客生效条款。

当前拟定值供经营者审阅；正式执行以保存并发布的政策版本和订单购买时接受的版本为准：

| 项目 | 当前拟定值 |
| --- | --- |
| 商品送达后普通退换货申请 | 30 个自然日 |
| 批准后交给承运商 | 14 个自然日 |
| 预计审核回复 | 2 个工作日 |
| 收货验收通过后预计发起退款 | 5 个工作日 |
| 现货订单处理 | 1–2 个工作日 |
| 承运商交运后预计配送 | 3–7 个工作日 |

个人原因要求未使用、未清洗、吊牌附件包装完整；质量问题、错发、运输损坏单独审核。拟定政策不收补货费，不因部分退货跌破门槛而补扣原包邮运费。详细文字见 [政策草稿](shop-shipping-returns-policy.md)。

### 8.2 审阅后发布

核对已保存草稿及经营信息，勾选页面的发布确认，再点击 **立即发布 / Publish now**。发布操作要求真实销售主体、完整客服和内容；缺失资料时按钮或接口会阻止发布。

发布后刷新 `/shop/policies` 并切换语言检查。以后改草稿不会自动替换已发布版本，需要再次审阅发布。历史订单按其原购买条款审核，不用今天的新政策改写原约定。

客服邮箱位于 **SnowForce policies → 客服邮箱**。前台首页页脚、商城顶部、政策页和订单详情会显示完整邮箱；首页页脚、商城顶部和政策页可直接点击邮箱，订单详情点击“联系客服”会附带订单号。政策发布后使用当前生效版本的客服邮箱；尚无生效政策或读取失败时显示经营者已确认的 `Shop@snow-force.com`。只修改草稿不会替换已生效的联系方式。

客服邮箱配置只保存联系方式，不会创建该邮箱或证明收发正常。发布政策也不会自动打开付款。具体版本行为见 [政策发布](shop-policy-publication.md)。

## 9. 商品分类和经营税务配置

这三个页面用于记录事实和审核资料；没有把所有州税率写成一个固定数值。当前许可状态尚未确认，不能仅为使按钮通过而勾选确认项。

### 9.1 商品税务分类

在 **SnowForce product tax** 选择商品，点击 **加载 Stripe 官方分类**，搜索并阅读适用说明，确认同款全部规格适用该类，填写依据并确认 **保存分类审核**。

不要只按商品名字猜类别或默认免税。当前不支持礼品卡、需要额外活动地点信息的类别和不同税务类别的混合组合商品。修改名称、描述或规格结构可能使审核失效；保存后若提示商品内容变化，重新审核。改价和库存不代替分类审核。

分类说明依据：[Stripe 官方税务分类](https://docs.stripe.com/tax/tax-codes)。后台自身的生效检查见 [商品分类说明](shop-product-tax-classifications.md)。

### 9.2 核对 Stripe 设置

进入 **SnowForce tax setup**，点击 **重新核对 / Check again**，检查：

- 当前账户及测试 / 正式环境。
- Tax Settings、缺少的设置、经营地址。
- 已生效销售税州及政府配送费用州。
- 页面列出的阻止条件和经营者确认状态。

该页只读，不申请政府许可证，不新增 Stripe 登记，也不收款。Stripe 内的测试资料不能作为正式许可依据。经营者须核实实际许可、登记及申报责任，技术人员据此配置对应正式环境。

### 9.3 经营税务资料

进入 **SnowForce business tax**，填写与已发布政策一致的正式主体，选择实际仓库，读取并审阅官方运费分类，填写审核依据，先 **保存草稿**。

仅在事实已核实后确认：有效加州销售许可、各州和渠道登记申报责任、运费税务处理。页面要求至少 20 个字符的审核依据；不要填写证件号码、税务密码或 API 密钥。

资料、政策、仓库及 Stripe 前置条件完整后，复核保存的版本，再选择 **启用经营税务配置**。保存草稿和启用是两个动作；启用也不代表整个商城已经验收或可以直接开放付款。仓库或政策变化可能要求重新审核。见 [经营税务配置](shop-business-tax-configuration.md) 和 [上线清单](shop-launch-status.md)。

## 10. 订单、收款和自行发货

**本节供整体上线验收通过后使用。当前没有真实订单可供演练。**

### 10.1 接单检查

从 **Orders** 打开订单，核对订单号、顾客、颜色尺码、数量、优惠后商品金额、运费、税费、总额、收货地址及原购买政策。区分订单状态、付款状态和配送状态，不能仅凭顾客截图或支付成功页面判定收款。

| 常见付款状态 | 操作含义 |
| --- | --- |
| Pending / Requires action | 付款尚未完成或需顾客操作，先核查 |
| Authorized | 付款已授权；尚不等于实际收款 |
| Captured / 已捕获 | 已执行收款；还需核对实际 Stripe 金额与对应订单 |
| Refunded | 检查对应退款及 Stripe 当前状态；页面标签不代表银行已经入账 |

### 10.2 全额收款

商城配置为先授权、后由管理员捕获。在原生订单 **Payment** 区域核对原付款和金额，再执行 **Capture**。原生入口参考：[订单付款](https://docs.medusajs.com/user-guide/orders/payments)。

当前成交税账仅支持**原订单一次全额捕获**。不要分次、部分捕获或使用手动标记付款绕过实际资金。原生后台的部分捕获全路径限制还未完成，因此出现相关按钮不代表本商城支持该操作。

收款后重新核对订单、Stripe 资金和 **SnowForce tax sales**。操作超时或报错，先刷新查看原付款结果；确认未知结果前不要再次新建付款或重复收款。

### 10.3 拣货、履约和交运

1. 核对款项、实际库存和地址。无法处理的地址先联系顾客，不能直接替顾客改成未经确认的地址。
2. 在订单 **Unfulfilled Items** 区域选择 **Fulfill items**，选正确仓库、配送方式、商品和数量。
3. 按实物拣货、复核 SKU、包装。建立履约记录表示安排了这些商品，不等于已交给承运商。
4. 自行购买面单，核对标签的地址、包装及追踪号，完成实际交运。
5. 在该订单 **Fulfillment** 区域建立 shipment，按窗口填写追踪号及可用的追踪链接，确认已寄出的商品数量。
6. 到会员订单核对顾客能看到正确的商品及追踪信息。
7. 承运商确认送达后，再使用 **Mark as delivered**。不要在打印面单时提前标记送达；送达时间会参与退换货期限审核。

分包裹寄出时，各履约记录和追踪号要对应准确商品数量。标记送达是不可逆操作，不能用来提前关闭发货任务。原生操作依据：[履约、发货和送达](https://docs.medusajs.com/user-guide/orders/fulfillments)。

### 10.4 通知和物流范围

本版提供自行发货和录入追踪信息，不提供已经验收的自动面单、自动承运商扫描或送达回传。运营人员需要跟进实际承运商状态。

系统的“Send notifications”选项不保证邮件已送达；当前邮件功能未完成验收。顾客主要在会员订单查看信息，额外邮件沟通由负责人按实际邮箱收发能力处理。

## 11. 退货、换货与退款审核

**本节的实际收货、库存、资金和换货发货操作，须在对应全流程验收通过后使用。退款税务冲销仍未完成。**

### 11.1 顾客入口与申请状态

顾客从 **我的订单 → 订单详情** 提交退货或换货，填写商品、数量、原因和说明；批准后填写退回承运商及追踪号。一个订单同时仅允许一个进行中的申请。

| 状态 | 下一步 |
| --- | --- |
| 待审核 / pending | 客服审阅；顾客可以撤销 |
| 已批准 / approved | 给出退回指引，建立并关联对应原生处理记录 |
| 处理中 / processing | 收货、资金核对、换货发货等实际处理 |
| 已完成 / completed | 收货、资金及换货送达核对通过 |
| 未批准 / rejected | 顾客可查看拒绝原因 |
| 已撤销 / cancelled | 申请已撤销 |

### 11.2 审核并回复

在 **SnowForce returns** 选择状态和申请，核对商品、数量、原因、申请日期、购买时政策与送达证据。普通超期或缺少证据的申请，需要明确例外及内部原因；质量问题或错发不会因普通期限自动拒绝。

填写 **顾客可见的回复**：是否批准、退回地址、商品条件、运费承担、交运期限及联系办法。**内部备注**用于工作人员记录，不会作为顾客回复公开。

点击 **批准并发送指引 / Approve** 或 **不批准 / Decline**。这里的“发送”是保存到顾客订单中的申请回复，本版不自动发邮件。批准不会自动创建退款、退货物流或替换商品。

批准回复可使用以下模板，发送前填写方括号内容并核对订单原条款：

> 你的退换货申请 [申请编号] 已批准，涉及 [商品、颜色/尺码及数量]。请按订单适用条件包装，并在 [交运截止日期] 前交给承运商。退回地址：SnowForce — Returns, 1 Park Plaza, #600 Office 44, Irvine, CA 92614, United States；包裹中请附订单号及申请编号。[退回运费承担方式]。寄出后请在会员订单填写承运商和追踪号。我们收到并验收后跟进 [退款或换货安排]。客服：Shop@snow-force.com。

### 11.3 建立并关联原生退货 / 换货

1. 申请批准后点击 **打开订单：收货、退款与换货发货**。
2. 在原生订单 Summary 的操作菜单建立 **Create Return** 或 **Create Exchange**。
3. 选择与申请完全一致的入库商品和数量、正确退回仓库；换货另选确认过的出库规格。
4. 回到 **SnowForce returns**，点击 **刷新关联选项**。
5. 选择对应处理记录，再点 **关联处理记录**。

系统会拒绝他人订单、数量或类型不符、取消记录和重复关联。不要把无关历史退货记录关联到本申请。原生入口依据：[退货](https://docs.medusajs.com/user-guide/orders/returns)、[换货](https://docs.medusajs.com/user-guide/orders/exchanges)。

### 11.4 收货、退款与换货

实际收到退回商品后，在原生订单登记验收数量，区分可再销售和损坏数量。不能只凭退回追踪号完成收货，也不能为损坏商品回补可售库存。

收货后先查看订单差额、原生付款退款记录及实际 Stripe 状态，再决定资金操作。不要把“已收货”当成银行到账证明；若已有成功或处理中退款，不要另点退款重复执行。原生收货、退款与通知可能因后续配置变化而联动，操作前必须核对确认窗口和现有资金结果。

退款按原商品优惠后实付及原订单适用条款处理，不按今天的商品价。部分退货金额适配、退款幂等恢复与税务冲销尚未完成，上线前由技术人员完成这些验收；不要手算一个金额绕过限制。

换货核对真实库存和顾客同意的颜色尺码。价差先说明并取得同意，再按经验证的原生流程处理；替换商品继续按履约、实际交运及送达记录操作。

### 11.5 核对并完成

在 **SnowForce returns** 点击 **核对 Stripe 款项**：该按钮只读 Stripe 并保存核对记录，不发起退款。结果可能是一致、处理中或需核查；原生付款资料改变后需要重新核对。

填写最终顾客回复，再点击 **核对并完成**。系统会实时复核：

- 对应退回商品已完成原生收货。
- 原生订单待处理差额为零。
- Stripe 实收与原生捕获金额一致，成功退款与原生退款合计一致。
- 没有 pending / requires_action 退款或查询失败。
- 换货的替换商品已送达。

任一未满足，保留处理中并调查。Stripe 成功也可能仍需银行入账时间。已有完成申请以后又出现款项异常，系统会记录核对异常，不自动重新打开申请；负责人需人工跟进。具体实现见 [退款最终状态核对](shop-refund-verification.md)。

## 12. 付款异常和成交税账

### 12.1 付款初始化中断

在 **SnowForce payments**：选择 **初始化中断 / Interrupted**，打开尝试，核对会话编号、金额、顾客和测试 / 正式环境。

在相同 Stripe 环境找到原 PaymentIntent，核对其 `metadata.session_id` 与页面会话一致。输入 `pi_…`，点击 **查询并核对 Stripe**，再审阅原付款状态、已收和可捕获金额。

核对一致并确认后点击 **保存核实关联**。这个操作关联原有付款，不新建、捕获或退款。成功后让顾客刷新原结账页面并核对订单；不要让顾客先创建第二笔付款。

不知道原付款是否存在时，先查原尝试；超过自动重试窗口或绑定不符时交由技术人员处理。界面提供 **重试原关联请求** 时使用该请求，不改变输入另建操作。见 [付款异常核对](shop-payment-operations.md)。

### 12.2 成交税账状态

在 **SnowForce tax sales** 查看订单、USD 金额、环境、尝试次数、错误和税账 ID：

| 状态 | 含义 | 工作方式 |
| --- | --- | --- |
| queued | 待记账 | 等待任务处理，关注是否长期停留 |
| running | 核对中 | 刷新观察，不另建记录 |
| retry | 等待重试 | 查看服务是否恢复；任务沿用原请求 |
| reconcile_required | 需要核对 | 核对原订单、实际资金和已有 Stripe 税账 |
| ready | 已记账 | 原成交及税账核验通过；不是申报已完成 |

当前后台运行时约每两分钟扫描持久任务；服务停机不会有任务处理，任务记录仍在数据库。**已捕获但尚未建立税账任务**的订单若持续出现，要检查是否部分捕获、多次付款或缺失原订单关联。

需要人工核对时，查找同账户、同环境、同订单对应的原税务交易，输入已有 `tax_…` 并点击 **核对已有税账**。这个按钮只查询并关联已有交易，不重复创建税务交易，不改变收退款；不能拿另一笔金额相同的交易充数。

已记账不等于已提交税务申报或缴款，退款也尚不具备完整自动税务冲销。详见 [成交税账](shop-tax-sale-ledger.md)。

| 无价格或不可加入购物车 | 对应规格的 USD 价格和可用库存 | 补正式美元价、库存位置及正确规格；不要关闭库存管理掩盖问题 |
| 中文没有跟着英文改变 | 中文双语对象 | 请技术人员维护数据库中的双语字段，不粘 JSON 字符串冒充对象 |
| 有货但网站缺货 | 仓库、销售渠道、预留和库存开关 | 核查真正可发位置的可用库存 |
| 不满 100 却显示包邮 / 应包邮却收费 | 折扣后商品金额、所选配送方式 | 在 SnowForce shipping 核对规则，税费不计门槛 |
| 填好 Stripe 密钥仍不能付款 | 政策、许可事实、分类、经营配置、Tax 设置与整体验收 | 按上线清单逐项处理，不只改付款开关 |
| 页面提示版本冲突或内容变化 | 其他管理员更新、商品 / 仓库 / 政策变化 | 保存自己的工作记录，重新载入，核对后再保存 |
| 保存中断，提供原请求重试 | 操作结果可能未知 | 使用界面原请求重试；不要连续新建重复命令 |
| 申请批准后没有退款 | 只完成了审核 | 检查原生收货和实际资金流程；批准不等于退款 |
| 不能完成退换货 | 收货、差额、资金或换货送达未满足 | 保持处理中，依据具体阻止项核查 |
| 顾客没有收到邮件 | 邮件服务尚未验收 | 检查会员订单中的回复，另行确认实际邮件收发 |
| 订单显示已退而款项不一致 | Stripe 当前退款结果及额外操作 | 使用款项核对并调查，不自动再退一次 |

## 14. 数据、权限和交接

### 14.1 信息保存在哪里

| 信息 | 保存位置与管理方式 |
| --- | --- |
| 商品、SKU、USD 价格、库存、订单、支付和物流 | 同一 Supabase PostgreSQL 的私有 commerce 分类，由 Medusa 后台管理 |
| 政策、经营税务资料、商品分类审核、异常核对与税账 | 同一私有 commerce 分类，由对应 SnowForce 页面管理 |
| 顾客登录 | 现有 Supabase Auth，沿用原会员账号和登录入口 |
| 顾客收货地址和会员订单读取 | 同一数据库的会员商城表，顾客只能访问自己的资料 |
| 商品照片 | 现有 Supabase Storage 的 shop-products bucket |

日常上架、调价和入库不需要修改代码。导入清单和脚本用于初始化，不是日常运营界面；不要重新导入或直接改表替代后台操作。

### 14.2 交接一条异常时需要什么

记录操作人、时间和时区、所在菜单、订单 / 申请 / SKU 编号、当前状态、问题文字、已执行动作和下一步。技术支持需要 Stripe 对应记录 ID 时，提供 ID 和测试 / 正式环境即可；不要提供密码、API 密钥、client secret 或完整顾客资料。

目前两名管理员拥有相同完整权限。新增员工、减少权限、正式邮箱通知、自动面单、中文商品编辑和公网部署需要另行配置与验收。本手册没有执行发布、收付款、发货、发信、数据库修改或权限变更。

### 14.3 发布前由负责人完成的最后核对

- [ ] 明确正式销售主体及实际许可、登记申报责任。
- [ ] 商品规格、正式 USD 价格、现货库存和分类审核完成。
- [ ] 政策保存、审阅、发布，客服邮箱收发已验证。
- [ ] 生产后台、域名、数据库连接、持久服务、备份与恢复已验收。
- [ ] 隔离 Sandbox 的购买、一次全额收款、订单库存、发货送达、申请退换、实际退款、税务冲销和故障恢复通过。
- [ ] 负责人确认开放收款，由技术人员核对生产配置后启用。

具体完成标准和未完成项目以 [商城上线清单](shop-launch-status.md) 为准。GitHub 提交成功、后台能打开或某个单独审核成功，都不替代这些步骤。

### 14.4 编写与核对依据

本手册的 SnowForce 页面名称、按钮、字段和限制依据项目 `services/commerce/src/admin/routes` 及对应后台服务；商品显示依据 `src/lib/shop/storefront.ts`；原生库存输入和 Metadata 限制依据安装包 `@medusajs/dashboard` 的实际表单。通用原生操作的官方链接放在相应章节。

本次为文档核对，没有执行真实订单的管理员浏览器操作。手册中面向正式交易的步骤仍需在完整交易验收中逐步核实，后续实现变化时同步更新本文件。
