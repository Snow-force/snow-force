# 商城税务报价的数据来源

更新：2026-10-02。已实现服务端报价来源复核、[固定请求与保存](shop-tax-quote-production.md) 和独立 [原子税费应用](shop-tax-quote-application.md)。顾客报价编排和过期/编辑恢复仍未连接；不会开启付款。

## 从哪里读取

| 数据 | 唯一来源 | 校验 |
| --- | --- | --- |
| 顾客和购物车归属 | 已验证的 Medusa customer 身份、原生 cart.customer_id | 先以最少字段查归属，再读取地址和金额；不接受浏览器指定的顾客 ID |
| 商品、数量、价格、优惠 | 原生购物车行和 adjustments | USD 精确美分、独立分币优惠分配，并与已安装 Medusa 的实际 totals 比较 |
| 配送范围、费用和包邮门槛 | 原生 shipping option、价格规则和 service zone | 每次读取数据库当前配置，核对实际收货州和已选运费；不使用导入初始值替代日常配置 |
| 商品税码 | 私有 Store metadata 的已审核分类，及原生已发布商品/规格 | 版本、商品内容、规格归属和审核指纹必须一致 |
| 发货地址、正式主体及审核确认 | 私有 Store metadata 的已启用经营配置、原生仓库及当前已发布政策 | 草稿不能作为许可确认；仓库地址和销售主体改变后需要重新审核 |
| Stripe 账户、模式、设置和登记 | 当前受保护商城密钥对应的 Stripe 只读 API | 完整分页、有效日期、US 类型和新鲜度；不接受顾客提交的登记或许可标记 |
| 报价时间 | 数据库 clock_timestamp() | 与刚读取的 Stripe 设置时间比较，避免使用任意浏览器时间 |

代码入口为 `services/commerce/src/lib/tax-quote-source.ts` 的 `readCartTaxQuoteSource`。输入只有服务端身份、购物车 ID 和取消信号；它不接收商品金额、税码或经营确认标记。报价字段明确排除支付会话的 data/client_secret，已有任何支付会话都停止重新报价。

税务地址和请求输入只返回服务端调用者，当前没有公开报价读取接口。数据继续来自现有 Supabase PostgreSQL 的私有 commerce schema，顾客仍使用网站的 Supabase 登录。没有增加顾客账户或公开税表。

## 金额和读取期间的变化

原价和保存的运费必须能准确表示为美元美分。运费读取不再把 9.955 自动舍入为 9.96；布尔值、null 和非 USD 价格也会拒绝。Medusa 原生 BigNumber 和精确十进制字符串仍可读取。

测试使用安装版本的 `decorateCartTotals` 生成购物车，覆盖 US$110 减 US$10.01 后商品金额 US$99.99、运费 US$9.95，以及减 US$10 后商品金额 US$100、运费 US$0。包邮按优惠后未含税商品金额判断。

读取 Stripe 设置期间，购物车、商品审核、政策主体、实际仓库、配送配置、region 或支付状态都可能被修改。服务在返回前重新读取这些来源；商品费用标记也进入来源指纹，不能在初次检查后把普通商品改成费用行而继续报价。归属改变、读取失败或取消请求都停止操作，错误信息不返回原始数据库、供应商或支付资料。

## 尚待接入的部分

- 原生百分比优惠可能产生半美分。已实现 [报价前金额归一化](shop-tax-money-normalization.md)，可在本人的受控事务中更新优惠和运费。严格来源读取仍拒绝未归一化金额；前台和实际报价处理器还没有自动连接该接口。
- 首版来源读取暂时拒绝含运费优惠、政府费用标记、自定义价格、礼品卡或含税标价的购物车。后续必须分别验证其表达方式；这不是这些功能已接入的声明。
- 返回前复核不能代替最终事务中的行锁。独立原子应用已在购物车锁和数据库锁下复核来源，统一写入原生税行、政府费用、应用记录及签名；先归一化、再报价、再应用的顾客自动编排尚未连接。
- 供应商请求处理器及 SQL 原子应用已实现。实际 Tax Calculation POST、顾客入口、过期报价清理、成交税交易和退款税冲销仍未完成验收；这些组件不代表付款路径已完成。

## 实际验证

上一阶段验证了 47/49 个报价字段。当前增加 credit_lines.id，共 50 个；实际 Medusa Query 接受这些字段和税率/费用属性字段，记录在 output/shop-tax-application-native.json。来源指纹还核对数字与原生 BigNumber 表示的一致性。缺失购物车只验证查询计划，不能代表实际顾客正向读取；独立只读 Stripe 核对用于确认当前设置状态。

实际数据库为 14 草稿商品、0 发布商品、0 订单、0 请求、0 报价、0 应用。Stripe 测试设置 pending、登记 0，付款开关关闭；隔离 SQL 验证写入最终全部回滚，没有永久业务写入。

金额和并发正向场景使用隔离数据及真实原生数学函数；原生 Query 验证使用缺失购物车。两者不能合称真实顾客购买或支付端到端验收。后续步骤和上线条件见 [上线状态](shop-launch-status.md) 与 [私有报价账本](shop-tax-quote-ledger.md)。
